## Range exploration — new findings (see docs/RANGE_INVESTIGATION.md)
Pushing beyond the tested band exposed that the documented −40…200 °C range
behaves in practice as roughly 0.1…100 °C:

- `-1.0` → `RANGE_HIGH` + `FAULTED`, with `wSetpoint1Write = 65526`.
  Root cause: gateway range-checked the **raw unsigned** word against 0–2000,
  so every negative setpoint was rejected. Fault direction was also mislabelled
  (`RANGE_HIGH` for a floor violation).
- `125.0` → reported accepted at every software layer (status 0, read-back
  1250, `IDLE`, `NO_FAULT`) but the **front panel did not follow**. Points at
  the F4S's own setpoint limits, which no code change can widen.
- `~100` behaved as a ceiling, consistent with the above.
- `99.0` → `NOT_ACCEPTED` with read-back stuck at `1000`. Root cause: confirm
  timeout (3.0 s) was shorter than the worst-case confirm chain (3.5 s).

Code fixes for the signedness, fault-direction and timeout defects are in this
commit. **The F4S device limits are still unmeasured** — run
`python-rtu-integration/probe_f4s_limits.py --sweep --yes` to establish them.
